# AI Agent 应用开发知识路线

> 定位：主投方向是 Agent 应用与工程，不是基础模型训练。  
> 目标：核心运行机制达到 L3，能独立实现、测试、观测和解释一个生产化最小 Agent。

## 1. 大模型应用基础

### P0（目标 L2）

必须掌握：

- Token、上下文窗口和消息结构；
- System / User / Assistant / Tool 消息角色；
- Temperature、采样和确定性边界；
- Structured Output 与 JSON Schema；
- 流式响应；
- 模型幻觉、延迟、吞吐和成本；
- 模型能力差异与路由基础；
- 外部输入和模型输出都属于不可信数据。

验收：不用 Agent 框架，完成一次带结构化输出、超时、错误处理和用量记录的模型调用。

## 2. Prompt 与 Context Engineering

### P0（目标 L2～L3）

Prompt 重点：

- 指令、背景、输入、约束、示例和输出协议；
- 指令层级和冲突；
- Few-shot 的适用边界；
- 模型不能代替程序约束。

Context 重点：

- 当前任务需要什么信息；
- 何时检索、截断、摘要或丢弃；
- 静态上下文、会话历史、工具结果和业务状态的区别；
- 上下文污染和提示注入；
- Token 预算；
- 上下文构造应可追踪、可测试。

验收：为同一个任务设计三种上下文策略，并比较准确性、延迟和成本。

## 3. Tool Calling

### P0（目标 L3）

必须掌握：

- Tool Schema：名称、描述、参数和返回协议；
- 工具选择由模型提出，程序负责校验和执行；
- 参数运行时校验；
- 工具注册、分派和权限；
- 工具结果如何回写上下文；
- 读操作与写操作的风险差异；
- 超时、重试、取消和幂等；
- 敏感操作需要人工确认；
- 工具错误应结构化，而不是伪装成普通文本。

独立实现：

```text
模型返回工具请求
→ 校验工具名称
→ 校验参数
→ 检查权限/确认
→ 执行
→ 记录耗时与结果
→ 结构化回写
```

## 4. Agent Loop 与运行时

### P0（目标 L3，最核心）

手写最小循环：

```text
接收任务
→ 加载业务状态
→ 构造上下文
→ 调用模型
→ 解析输出
→ 执行零个或多个工具
→ 写回结果
→ 判断继续、暂停或结束
→ 持久化状态与 Trace
```

必须处理：

- 最大轮数和终止条件；
- 状态持久化；
- 进程中断后恢复；
- 等待用户确认；
- 工具失败和部分成功；
- 重复执行防护；
- 并发任务隔离；
- 取消与超时；
- 模型输出不符合协议；
- 无意义循环和成本失控。

验收：不使用 LangGraph，独立完成可恢复、可追踪的单 Agent Tool Loop。

## 5. Workflow 与 Agent 的边界

### P0（目标 L2～L3）

必须区分：

- 确定性 Workflow：步骤由代码和状态机决定；
- 动态 Agent：模型在受约束的行动空间中决策；
- 混合模式：确定性骨架 + 局部模型决策。

选择原则：

- 能用确定性代码解决的，不交给模型；
- 高风险写操作采用固定流程和人工确认；
- 模型适合语义理解、归纳、选择和生成；
- Workflow 负责可靠执行和恢复。

P1：学习 LangGraph 或当前主流运行时，用它表达已理解的状态、节点、中断和恢复，而不是用框架替代理解。

## 6. RAG

### P0（目标 L3）

完整链路：

```text
文档获取
→ 解析/清洗
→ 切分
→ 元数据
→ Embedding/索引
→ Query 理解
→ 召回
→ Rerank
→ Context 构造
→ 生成与引用
→ 评测
```

必须掌握：

- Chunk 大小和重叠的取舍；
- 向量检索、关键词检索和混合检索；
- 元数据过滤；
- Top K 与上下文预算；
- Rerank；
- 文档版本、删除和更新；
- 引用必须映射到真实来源；
- 检索失败与生成失败分开评估。

验收：建立小型文档集和测试问题，记录 Recall@K、引用正确性和最终回答质量。

## 7. Memory

### P1（目标 L2）

需要区分：

- 当前执行状态；
- 短期会话历史；
- 长期用户偏好；
- 业务数据库事实；
- RAG 知识库。

核心问题：

- 写入什么；
- 什么时候写；
- 如何读取；
- 如何纠错和遗忘；
- 谁可以访问；
- 如何避免把模型猜测当事实保存。

Memory 不是简单保存全部聊天记录。

## 8. MCP

### P0：概念和最小实践（目标 L2）

必须理解：

- MCP 解决工具和上下文接入的标准化问题；
- Client、Server 和 Host 的职责；
- Tools、Resources、Prompts 的区别；
- 本地进程和远程服务的信任边界；
- MCP 不等于 Agent，也不自动解决权限、重试和业务幂等；
- 直接 API、内部 Tool Registry 与 MCP 的取舍。

验收：实现或接入一个最小 MCP Server，并说明不用 MCP 时的替代设计。

## 9. Evaluation

### P0（目标 L3）

必须先定义“成功”再优化 Agent。

评测层次：

### 组件级

- 结构化输出合法率；
- 工具选择正确率；
- 参数正确率；
- 检索 Recall@K；
- Rerank 效果。

### 任务级

- 任务完成率；
- 最终答案正确性；
- 引用正确性；
- 用户需要纠正的次数；
- 副作用是否符合预期。

### 系统级

- 延迟；
- Token 和费用；
- 工具失败率；
- 平均循环轮数；
- 中断恢复成功率。

需要掌握：

- 固定测试集；
- 规则评测、代码评测、人工评测和模型评测的边界；
- 回归测试；
- 失败样本分类；
- 离线评测与线上反馈。

验收：为项目建立至少 20 个可重复运行的测试样本和自动化指标。

## 10. Tracing 与可观测性

### P0（目标 L3）

一次 Agent 执行至少记录：

- Task / Run ID；
- 输入、模型、提示版本；
- 上下文来源；
- 每次模型调用；
- 工具参数、结果和耗时；
- 状态迁移；
- Token、费用和延迟；
- 错误、重试和人工确认；
- 最终输出。

Trace 不只是调试日志，还服务于评测、回归和成本分析。

## 11. 安全、权限与可靠性

### P0（目标 L2～L3）

- Prompt Injection；
- 间接注入：网页、文档和工具结果中的恶意指令；
- 工具最小权限；
- 读写隔离；
- 高风险操作确认；
- 沙箱和资源限制；
- 敏感信息不进入不必要的上下文；
- 输出过滤不能替代权限控制；
- 审计日志；
- 超时、重试、幂等和补偿。

## 12. 多 Agent

### P2（目标 L1）

只在出现明确需求时使用：

- 上下文隔离；
- 权限隔离；
- 不同工具集；
- 并行工作；
- 独立评测和责任边界。

不因为“复杂”就拆多 Agent。多 Agent 会增加通信、状态、一致性、成本和调试难度。

## 13. 碎片化学习任务

### S 型（10～15 分钟）

- 为一个工具写 Schema；
- 判断一个步骤应由代码还是模型负责；
- 分析一条 Trace；
- 设计一个评测样本；
- 解释 MCP 与 Tool Calling 的区别。

### M 型（20～30 分钟）

- 写模型调用封装；
- 实现工具参数校验和分派；
- 画 Agent 状态机；
- 设计一个 RAG 切分或检索实验；
- 为失败场景设计恢复策略。

### L 型（30～45 分钟）

- 接通一次 Tool Calling；
- 完成 Agent Loop 的一个纵向切片；
- 接入 Trace；
- 跑一组评测并分析失败样本。

## 14. Agent 验收门槛

投递前至少能够：

- 手写带工具调用、终止条件、状态保存和 Trace 的 Agent Loop；
- 解释 Tool Calling、MCP、RAG、Memory 和 Workflow 的边界；
- 建立可重复的评测集，而不是只展示成功 Demo；
- 处理工具失败、模型格式错误、超时、重复执行和人工确认；
- 从准确性、延迟、费用、安全和可恢复性比较方案。
