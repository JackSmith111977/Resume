# AI Agent 应用开发知识路线 v2

> 定位：主投 Agent 应用与工程，不是基础模型训练。  
> 目标：理解必要模型基础，独立实现、测试、观测和解释一个最小 Agent 系统，并能使用一个主流框架复刻。

## 1. 必要模型基础（P0，目标 L1）

不要求训练基础模型，但必须能解释：

- Tokenization、Token 和上下文窗口；
- Embedding 表示什么、相似度不等于事实正确；
- Transformer 与 Attention 解决的大致问题；
- 自回归生成和概率采样；
- Temperature、Top-p 和确定性边界；
- In-context Learning、Prompt、RAG、SFT、LoRA 的用途差异；
- 推理模型与普通生成模型在延迟、成本和控制方式上的工程差异；
- 何时应该 RAG，何时考虑微调，何时只需要确定性程序。

验收：面对一个业务任务，能比较 Prompt、RAG、工具、规则和微调的适用边界。

## 2. 模型调用与结构化输出（P0，目标 L2）

必须掌握：

- System / User / Assistant / Tool 消息；
- Structured Output 与 JSON Schema；
- 流式响应；
- 超时、重试、限流和取消；
- Token、延迟、费用和模型版本记录；
- 模型输出属于不可信输入；
- 业务约束必须由程序校验，不能只写在 Prompt 中。

验收：不用 Agent 框架完成一次带结构化输出、运行时校验、超时、错误处理和用量记录的模型调用。

## 3. Prompt 与 Context Engineering（P0，目标 L2）

- 指令、背景、输入、约束、示例和输出协议；
- 指令层级、冲突和 Prompt Injection；
- 静态上下文、会话历史、检索结果、工具结果和业务状态；
- 检索、截断、摘要和丢弃；
- Token 预算和上下文污染；
- Context 构造必须可追踪、可测试和可版本化。

验收：为同一任务设计两种上下文策略，比较正确性、延迟、成本和污染风险。

## 4. Tool Calling（P0，目标 L3）

必须掌握：

- Tool Schema：名称、描述、参数和返回协议；
- 模型提出工具请求，程序负责校验和执行；
- 工具注册、分派和版本；
- 参数运行时校验；
- 读写工具的风险差异；
- 权限、人工确认和审计；
- 超时、取消、重试和幂等；
- 工具错误必须结构化；
- 工具结果写回上下文前仍需视为不可信数据。

最小执行链：

```text
模型提出工具请求
→ 校验工具名
→ 校验参数
→ 检查权限/确认
→ 执行
→ 记录结果、耗时和副作用
→ 结构化回写
```

## 5. Agent Loop 与 Runtime（P0，目标 L3）

手写最小循环：

```text
接收任务
→ 加载状态
→ 构造上下文
→ 调用模型
→ 解析输出
→ 执行零个或多个工具
→ 持久化结果与 Trace
→ 判断继续、暂停或结束
```

必须处理：

- 最大轮数和终止条件；
- 格式错误和未知工具；
- 工具失败和部分成功；
- 超时、取消和重复执行；
- 等待用户确认；
- 状态持久化和进程中断；
- 并发任务隔离；
- 无意义循环和成本失控。

验收：不用 LangGraph 等框架完成一个可追踪、有限循环、可注入失败的单 Agent Tool Loop。

## 6. Workflow 与 Agent 边界（P0，目标 L2）

- 确定性 Workflow：步骤和状态迁移由代码决定；
- 动态 Agent：模型在受约束行动空间中决策；
- 混合模式：确定性骨架 + 局部模型判断。

选择原则：

- 能用确定性程序解决的，不交给模型；
- 高风险写操作使用固定流程和人工确认；
- 模型用于语义理解、归纳、选择和生成；
- Workflow 负责可靠执行、恢复和审计。

## 7. 主流框架最低熟悉度（P0，目标 L2）

在手写最小 Loop 后，选择一个当前主流 Agent Runtime / Workflow 框架复刻同一流程。

必须能解释：

- 状态、节点、边和中断如何表达；
- 框架提供了哪些持久化、Trace 或恢复能力；
- 哪些错误和状态被框架隐藏；
- 项目采用或不采用该框架的理由；
- 如何脱离框架定位底层模型或工具问题。

不要求同时学习多套框架，不把框架 API 记忆当作核心能力。

## 8. RAG（P0，目标 L2～L3）

链路：

```text
文档获取
→ 解析与清洗
→ 切分与元数据
→ 索引
→ Query 理解
→ 召回
→ Context 构造
→ 生成与引用
→ 评测
```

必须掌握：

- Chunk 大小和重叠；
- 向量、关键词和混合检索的差异；
- 元数据过滤；
- Top K 和上下文预算；
- 文档版本、更新和删除；
- 引用必须映射真实来源；
- 检索失败和生成失败分开评估；
- Rerank 是 P1，先证明基础召回确有问题。

验收：建立公开小型文档集和测试问题，记录 Recall@K、引用正确性和最终任务完成情况。

## 9. Evaluation（P0，目标 L3）

### 组件级

- 结构化输出合法率；
- 工具选择和参数正确率；
- 检索 Recall@K；
- 引用映射正确率。

### 任务级

- 任务完成率；
- 最终答案正确性；
- 用户纠正次数；
- 副作用是否符合预期。

### 系统级

- 延迟、Token 和费用；
- 工具失败率；
- 平均循环轮数；
- 超时和恢复情况。

必须掌握固定测试集、规则评测、代码评测、人工评测和模型评测的边界，以及回归和失败样本分类。

验收：首版至少 10～20 个可重复样例，并能说明数据集的覆盖缺口。

## 10. Tracing 与可观测性（P0，目标 L3）

一次执行至少记录：

- Task / Run ID；
- 模型、Prompt 和数据集版本；
- 输入和上下文来源；
- 每次模型调用；
- 工具参数、结果、耗时和错误；
- 状态迁移；
- Token、费用和延迟；
- 最终输出和评测结果。

Trace 不是只打印日志，还用于复盘、回归、成本分析和安全审计。

## 11. 安全、权限与可靠性（P0，目标 L2）

- Prompt Injection 和间接注入；
- 工具最小权限；
- 读写隔离；
- 高风险操作确认；
- 沙箱、超时和资源限制；
- 敏感信息最小化进入上下文；
- 输出过滤不能替代权限控制；
- 审计日志；
- 重试、幂等和补偿。

## 12. MCP（概念 P0，实践 P1）

P0 只要求理解：

- Host、Client、Server 的职责；
- Tools、Resources、Prompts 的区别；
- MCP 解决接入标准化，不等于 Agent；
- MCP 不自动解决权限、重试、幂等和业务状态；
- 直接 API、内部 Tool Registry 和 MCP 的取舍。

接入最小 MCP Server 属于 P1。复杂远程 MCP、安全部署和多服务治理属于 P2。

## 13. Memory（P1）

区分：

- 当前执行状态；
- 会话历史；
- 长期用户偏好；
- 业务数据库事实；
- RAG 知识库。

核心问题是写什么、何时写、如何纠错、如何遗忘和谁能访问，而不是保存全部聊天记录。

## 14. 多 Agent（P2）

只有出现明确的上下文、权限、工具集、并行或责任隔离需求时才使用。多 Agent 会增加通信、状态、一致性、成本和调试难度。

## 15. 投递前验收

- 能解释必要模型基础和 RAG/微调边界；
- 手写最小 Agent Loop；
- 用一个主流框架复刻并比较；
- 完成 Tool + RAG + Citation + Trace + Eval 闭环；
- 覆盖格式错误、工具错误、超时和引用错误；
- 能从准确性、延迟、成本、安全和恢复做方案取舍。
