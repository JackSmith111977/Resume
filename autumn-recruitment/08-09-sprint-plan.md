# 8 月～9 月初秋招冲刺计划

> 时间范围：2026-08-03 ～ 2026-09 初  
> 学习场景：以工作日实习期间的碎片时间为主，不依赖周末集中学习  
> 目标：开始投递前形成 AI Agent / 全栈 / 前端三方向的最低竞争闭环。

## 1. 总策略

不追求全面学完，而追求形成面试闭环：

```text
算法门槛
+
后端系统理解
+
Agent 工程能力
+
项目与面试表达
```

计划必须适配实习期间的不确定空档，因此所有任务都应满足：

- 10～45 分钟内能完成一个独立检查点；
- 中断后能够根据记录继续；
- 每次只处理一个具体问题；
- 阅读必须转化为口述、代码、图或复盘记录；
- 周末不承担必做任务，仅作为休息或可选补偿时间。

---

# 2. 工作日碎片时间模型

不绑定固定钟点，根据当天实际空档选择对应任务。

## S 型：10～15 分钟

适合低启动成本任务：

- 无标签判断一道算法题的候选模式；
- 复述一个知识点；
- 手算一个算法用例；
- 阅读并压缩一段官方文档；
- 补一张知识卡片；
- 回答一道项目追问。

## M 型：20～30 分钟

适合需要完整思考链的任务：

- 写算法思路、状态和不变量；
- 实现一道简单题或中等题的核心部分；
- 画一条请求链路或 Agent Loop；
- 写一个接口、SQL 或 Tool Schema；
- 为已有代码补测试和错误处理；
- 完成一次小范围知识诊断。

## L 型：30～45 分钟

适合连续编码与整合：

- 独立完成一道中等算法题；
- 实现一个最小后端接口；
- 实现一次模型调用或 Tool Calling；
- 接通项目中的一个最小纵向切片；
- 完成一次混合模拟面试。

如果当天只有短空档，就累计完成多个 S 型任务；不因缺少长时间段而中断整周计划。

---

# 3. 每周固定五日循环

每周使用同一节奏，降低决定“今天学什么”的成本。

| 工作日 | 主任务 | 次任务 | 最小产出 |
| --- | --- | --- | --- |
| 周一 | 算法模式识别 | 复盘上周错误 | 2～3 道题的推导卡 |
| 周二 | 后端知识与链路 | 算法间隔复现 | 一张链路图或一个最小接口 |
| 周三 | 算法独立实现 | Agent 概念/原理 | 1 道完整实现 + 1 张 Agent 卡片 |
| 周四 | Agent 编码或项目纵切 | 后端可靠性 | 一个可运行检查点 |
| 周五 | 混合诊断与面试表达 | 更新看板 | 本周验收记录与下周调整 |

算法保持高频出现，但不占用全部时间；后端和 Agent 采用交替推进，避免长期只学一条线。

# Week 0：基线诊断（8/3 - 8/9）

## 目标

明确真实短板，并建立适合碎片时间的任务队列。

## 工作日任务

### 算法

拆成六次 M 型诊断，每次只做一个专题的代表题：

- 滑动窗口；
- 二分；
- 树与图；
- 回溯；
- 动态规划；
- 单调栈。

每题记录：

```text
是否识别模式
是否能定义状态
是否能独立实现
是否依赖原题解记忆
最终卡点
```

### 后端

用 S/M 型任务扫描：

- Spring Boot 请求链路；
- Controller / Service / Repository；
- MySQL 索引和事务；
- Redis 用途；
- 幂等、重试、异步任务和状态机。

### Agent

用 S/M 型任务检查能否解释：

- 模型调用与消息结构；
- Structured Output；
- Tool Calling；
- Agent Loop；
- RAG；
- MCP；
- Evaluation。

### 简历与项目

每个空档只补一个问题：

- 背景是什么；
- 原方案有什么问题；
- 自己做了什么；
- 为什么这样设计；
- 结果和可验证证据是什么。

## 产出

- 算法能力雷达；
- 后端和 Agent 缺口清单；
- 实习与项目素材清单；
- 下一阶段任务优先级。

# Week 1：算法恢复 + 后端基础（8/10 - 8/16）

## 算法

重点从答案记忆转向模式识别与重新推导：

- 哈希；
- 双指针；
- 滑动窗口；
- 栈；
- 二分。

每次空档只完成一个步骤：

```text
提取题目性质
→ 写暴力方案
→ 找重复计算
→ 选择模式
→ 定义状态与不变量
→ Python 实现
→ 手动测试
```

不要求一次空档完成整题，可以通过检查点跨多个空档续写。

## 后端

依次完成：

- 一次 HTTP 请求进入 Spring Boot 后的完整链路图；
- 一个 Controller / Service / Repository 最小实现；
- 一个带参数校验和统一异常处理的接口；
- 一组 MySQL 表、索引和查询设计；
- Redis 在缓存、幂等或状态存储中的一个具体应用。

## 验收产物

- 5～8 张算法推导卡；
- 至少 2 道无标签题独立实现；
- 一个可讲清楚的后端接口纵向切片。

# Week 2：后端可靠性 + Agent 最小闭环（8/17 - 8/23）

## 后端

围绕一个非保密的“文件处理任务”案例，分空档完成：

```text
创建任务
→ 文件提交
→ 异步处理
→ 状态查询
→ 结果返回
→ 失败恢复
```

逐个补齐：

- 状态机；
- 幂等键；
- 超时；
- 重试与退避；
- 重复消费；
- 失败状态；
- 日志与追踪字段。

## Agent

不使用大型框架，分成多个最小检查点：

1. 调用一次模型；
2. 获取 Structured Output；
3. 定义一个工具 Schema；
4. 校验并执行工具参数；
5. 将工具结果写回上下文；
6. 支持继续或结束；
7. 增加最大循环次数、超时和 Trace。

## 验收产物

- 一份异步任务系统设计；
- 一个可运行的最小 Agent Loop；
- 能口述 Agent Loop 中每个状态的含义和失败点。

# Week 3：Agent 工程化 + 项目纵向切片（8/24 - 8/30）

## Agent 工程化

拆分学习与实现：

- 文档解析与 Chunk；

- 向量或混合检索；
- Rerank；
- Citation；

每个主题至少完成一种证据：

- 最小代码；

- 对比表；
- 小型评测结果。

## 项目纵向切片

不先建设完整平台，只接通一个用户可见闭环：

```text

→ 一个工具或一次检索
→ 流式/最终结果
→ Trace 记录
```

之后再添加：

- 状态持久化；
- 超时与重试；
- 人工确认；
- 简单评测集。

## 验收产物

- 项目架构图；
- 技术方案；
- 一个可演示的纵向切片；
- 至少 5 条评测样例。

# 5. 工作日任务队列规则

任务按三列维护：

| Ready | Doing | Review |
| --- | --- | --- |
| 已拆到 45 分钟内，可直接开始 | 当前最多一个编码任务和一个轻任务 | 等待间隔复测或口述验收 |

规则：

- Doing 中不要同时堆积多个大型主题；
- 新知识必须先拆成 S/M/L 任务再进入 Ready；
- 完成不等于看完，必须有可验证产物；
- 周五统一清理 Review，并决定哪些内容进入下周复测；
- 周末没有必做任务，未完成内容重新拆分后进入下一周，不以牺牲休息补齐。

# 6. 验收标准

9 月初前至少达到：

- 隐藏专题后，常见算法题能在 5 分钟内提出方向和不变量；
- 能在 20～30 分钟内用 Python 独立完成基础到中等题；
- 能解释并设计后端完整请求、异步任务和失败恢复链路；
- 能脱离大型框架实现最小 Agent Loop；
- 有一个打通前端、后端、工具/RAG 和 Trace 的 Agent 纵向切片；
- 能从前端、全栈和 Agent 三种视角讲解同一项目。

## 计划失效条件

出现以下情况时应调整，而不是硬追进度：

- 实习工作量使每日空档持续低于 20 分钟；
- 算法诊断显示 Python 实现而非模式识别才是主要瓶颈；
- Agent 项目选题范围过大，两个工作日仍无法完成一个纵向检查点；
- 简历或笔试提前开始，需要提高投递和算法权重。
